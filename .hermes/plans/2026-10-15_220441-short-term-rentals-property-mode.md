# Property Peace Long-Term + Short-Term Rental Implementation Plan

> **For Hermes:** Use the `subagent-driven-development`, `property-peace-development`, and `test-driven-development` skills when implementation is authorized. This document is a plan, not authorization to build, migrate, enable payments, or deploy.

**Goal:** Let owners choose **Long-term rental** or **Short-term rental** when adding a property, assign the mode to each independently managed unit, change a unit's mode later under safe rules, and see fields and workflows appropriate to its mode. Grow the short-term mode into direct booking, a consolidated availability calendar, guest communications, owner reporting, and a digital guidebook without disrupting existing lease-based management.

**Architecture:** Keep a single Property Peace account and property record. Store rental *mode* on each independently managed unit, independent of the existing structural `PropertyType` (`SingleFamily`/`MultiUnit`); do **not** rename or overload that enum. The property-creation choice is the initial default for its units, not a property-wide constraint; a single-family home still needs an inventory record representing its rentable home. Preserve long-term behavior as the default for all existing inventory. Keep leases/tenants and reservations/guests as separate domain models, sharing property/unit inventory, expense and maintenance infrastructure where appropriate. The API, not just conditional UI, enforces mode-specific rules.

**Tech stack:** Existing ASP.NET Core/EF Core API and SQL Server; React web app; Expo/React Native mobile app. Use existing organization authorization, property-entitlement and feature-readiness conventions.

---

## Decisions confirmed with Thomas

- Property Peace will support normal long-term rentals and short-term rentals under the same product.
- Property creation offers a short-term option; owners can change the mode after creation.
- Mixed-use buildings are supported: each independently managed unit has its own mode; the creation choice initializes units but does not force every unit in a building to stay the same. Single-family homes use one managed inventory record.
- The visible fields depend on each unit's mode. A landlord's profile/portfolio view adapts to **long-term only**, **short-term only**, or **both**, without hiding a mixed property's other units.
- Mode changes are allowed only after blockers are resolved. A preflight popup explains the specific lease, booking, payment, or guest obligation to fix; no data is silently removed.
- Short-term owners can create listings, set nightly prices and manage availability before payment approval. **Guest booking and online payment are one gated flow:** guests cannot request, reserve or confirm a direct booking until the payee's application is approved by a Property Peace admin, Stripe Connect onboarding/verification is complete, and Property Peace has approved online collection for that payee. An owner submits an expanded application (including a freshly captured license image and selfie); no owner-facing or API path to Connect signup exists before application approval. Application approval alone does not enable booking or charges.
- Desktop applicants can use a secure, expiring, one-use QR/mobile handoff for the in-session camera capture. A device photo library or file upload is not offered in this flow; camera capture is not itself proof of identity or liveness, so manual review and/or an approved identity-verification provider is still required.
- Short-term listings should feel like listings for stays (photos, nightly price, calendar, amenities, house rules, check-in/out) rather than a renamed long-term lease listing.
- Calendar entries show source, sync status, and **last successful sync date/time** (including timezone), plus stale-sync warnings.
- Property Peace checkout is for **new direct bookings made through Property Peace**. This is not a flow to reroute payment on existing Airbnb/Vrbo/Booking.com bookings.
- Later short-term capabilities: direct booking/secure payment, unified availability and blocks, guest messages, performance dashboard, digital guidebook.
- Use **Lease** and **Tenant** only for long-term rentals. For short-term rentals, use **Booking** in the owner interface, **Reservation** in guest-facing details and confirmations, **Stay** for the checked-in period, and **Guest** for the person booking. A guest may accept house rules or a rental agreement, but that document does not turn a booking into a lease.

## Product model and field matrix

| Area | Shared | Long-term only | Short-term only (as the phases become real) |
| --- | --- | --- | --- |
| Property basics | Name, address, structural building type, photos, contacts/manager, expenses, maintenance | — | — |
| Inventory | Units where applicable; the bookable inventory must be explicitly defined | Leaseable unit | Bookable unit/listing (do not assume every multi-unit property is one bookable listing) |
| Pricing | Currency, property ownership | Monthly target rent, target deposit, lease terms | Nightly base price, minimum nights, cleaning fee, taxes/fees, check-in/out times, timezone; validate availability before publish |
| People & work | Authorized staff, maintenance | Tenants, leases, rent collection, move-in/out | Guests, reservations, stays, turnovers, guest communication |
| Owner view | Property-specific expenses and financial context | Occupancy/rent roll/lease status | Calendar, occupied nights, booking revenue, expenses, profit with stated accounting basis |
| Publishing | Private owner record first | Existing long-term listing flow | Distinct short-term listing with photos, amenities, rules, nightly prices and calendar; the guest-facing **Book** action and booking API stay closed until online collection is fully approved and enabled |

Start with a **small creation form** (mode, address, name, structural type, shared details) and show only relevant fields or a clearly labeled "Set up short-term rental" section. Owners can prepare real pricing, calendar and listing details before approval, with a clear "Bookings unavailable until online payments are approved" status. Do not expose a live booking CTA or guest reservation API until the full collection gate passes. Keep the payment application separate from initial property creation. Preserve mode-specific data on a reversible switch; never silently erase leases, reservations, rates, or guidebooks when a panel becomes hidden.

## Phase 0 — Contract, domain, and conversion rules

1. Inventory every active web/mobile add/edit entry point, API property projection, unit/listing creation path, dashboard selector, filter, and property-limit calculation. Confirm how an existing single-family property maps to its managed unit, and whether multi-unit properties already represent every independently bookable space. Record current JSON enum casing and model binding.
2. Define a dedicated enum, e.g. `ERentalMode.LongTerm` / `ShortTerm`, persisted on the managed unit as a string, with SQL default `LongTerm` for existing rows. Set explicit default for omitted create payloads to retain legacy clients. Ensure updates from older clients that omit rental mode **preserve** the existing value instead of resetting it; a dedicated unit-mode-change command/endpoint is preferable to changing the existing full-property POST semantics. The creation-level choice populates unit defaults; it does not create a contradictory second source of truth on Property.
3. Define per-unit mode-switch policy and test it before UI: never delete associated data; block a long→short switch with active/scheduled leases or tenant obligations on that unit until safely closed; block a short→long switch with upcoming/active reservations or unresolved guest/payment obligations on that unit. Historical data remains accessible/auditable. Reversing an empty unit's change is allowed. Before a blocked attempt, show a **popup naming each blocker and its resolution action** (e.g. lease end, future reservation cancellation/refund, pending charge/dispute); do not offer an override that bypasses server validation. For a safe change, show a distinct confirmation explaining hidden workflows and retained history. Do not block a safe unit because another unit in the building has an active lease or stay. Property summaries must represent mixed modes rather than pretending the whole building is one type.
4. Clarify that `IsOccupied`/rent-roll and unit entitlements have long-term semantics; agree on how short-term inventory counts against the existing 5-unit free plan before migration. Existing users must not be charged or locked out simply because a rental-mode column was added. Define the portfolio capability model from the **authorized organization's actual inventory**: `longTermOnly`, `shortTermOnly`, `mixed`, or `empty`, with unit-level routing and role-specific permissions. Do not make a stale editable user-profile flag the source of truth.

**Acceptance:** Documented defaults, switch preconditions and actionable popup messages; a migration/backfill strategy with a safe rollback path; no payment or reservation promise in phase 1.

## Phase 3 — Payment application, admin decision, Connect onboarding and online checkout

17. Add a **Short-term online collection application** accessible only to authorized property owners/managers, but not a Stripe signup link. Collect legal business/individual identity and role, contact and property details, proof of ownership/management and payout authority, business model/expected booking volume, cancellation/refund policy, guest support contact and risk disclosures. Decide minimum necessary fields and legal basis with compliance counsel; do not collect bank credentials or raw Stripe KYC unnecessarily. Track immutable submission/version, reviewer and timestamps. Application statuses: `draft → submitted → under_review → more_information_requested → approved | rejected`; changes to bank/owner/authority or suspicious activity can suspend/reopen review. Support resubmission and a clearly described rejection/appeal route.
18. Add **fresh camera capture** for a government-issued license/ID and a selfie as part of the application. On mobile, request camera permission and invoke an in-app camera-only capture; do not show gallery/photo-library/file-picker options. On desktop, use an in-browser webcam when available **or** issue an authenticated, expiring, one-use QR handoff bound to the applicant, application and browser session; mobile web opens the camera-only capture, uploads over TLS, and signals completion back to desktop after server validation. No anonymous reusable link, raw ID in URL, cross-account attachment or public media URL. Provide accessible retry/error and a secure assisted-review fallback when camera access is unavailable; a UI-only camera restriction cannot prevent screen replay, rooted-device spoofing or prove liveness. Decide whether a certified identity-verification provider should handle capture/liveness/document checks instead of building this in-house; manual/third-party verification is mandatory, not an automatic approval from two images.
19. Route ID/selfie evidence to an approved identity provider where feasible; otherwise use encrypted private storage, narrowly scoped signed access for trained admins, malware/type/size validation, encryption at rest and in transit, no raw images in logs/analytics, short documented retention/deletion and consent/privacy disclosures. Stripe should collect its own required KYC through Stripe-hosted onboarding; Property Peace should store reference IDs, decisions and minimal evidence/status, not replicate or publicly expose Stripe identity data. Legal/privacy review must precede collection, including retention and biometric/liveness requirements where applicable.
20. Build an **admin-only review queue** with organization/property context, evidence and authority checks, request-more-info/approve/reject/suspend actions, reason codes, reviewer identity, audit history and dual control/escalation for risky cases. Owner-facing status page shows exactly what's missing and next steps; do not reveal sensitive fraud signals. Verify management authority independently; `details_submitted` and automated ID matching alone are not approval.
21. Enforce the backend state machine: until `application_approved`, deny every Connect account creation/linking/onboarding session and onboarding URL (including legacy entry points). After admin approval, permit **Stripe Connect signup**; only after Stripe's verified capabilities, no unresolved restrictions/due requirements, an approved authorized payout destination and explicit Property Peace `payout_approved` may the system enable **both guest booking and online collection**. Before this final gate, deny booking/hold creation, payment-intent/payment-link creation and any guest charge at the API—not just hide a button. Lock down direct API calls, webhook transitions, retries and concurrent approvals. Recheck eligibility when starting checkout and before confirmation/capture; suspension blocks new bookings and charges while preserving existing reservations for support/refund handling. Account existence or a previously created Connect account is never enough to turn either feature on. Apply the payment policy consistently to Property Peace collection flows; assess impact on existing long-term rent gates before implementation.
22. Define quote rules before coding: nightly rates, date overrides, minimum stays, discounts, cleaning fees, taxes, security deposits, refunds/cancellations and all-in price display. Once fully enabled, implement guest date selection → current price quote → transactional availability hold → secure payment → webhook-reconciled **confirmed paid** reservation as an idempotent business flow. Failed/expired checkout releases its hold; a payment success with a delayed webhook must reconcile safely without losing the guest's booked nights. Keep pending checkout holds internal and time-limited; do not create an unpaid confirmed guest booking or a request-to-book option. Keep reservations/guests distinct from lease/rent payment records.
23. Define guest-facing checkout, confirmation emails, privacy/identity and fraud controls, accessibility, support and dispute flows. **Payment ownership/payout model and money movement require a dedicated security/compliance review**: verify merchant-of-record, Connect capabilities/authorization, owner/manager authority, KYC, delayed holds, manual payouts for new payees, reversals, fraud and taxes; current Property Peace payment gates stay off until redesign/testing criteria are met. Channel-origin reservations remain governed by their channel's payment rules. Prove two guests cannot confirm the same nights, webhook retries cannot duplicate charges/bookings, and a paid guest always receives a recoverable confirmation or refund workflow. Publish only after sandbox-to-production and operational readiness gates.

## Superseding decision — 2026-10-21 (short-stay collection and direct booking)

This decision supersedes the approval-before-Connect and mandatory Property Peace identity/application gates described in Decisions confirmed, Phase 2/3, validation gates and open decisions above; those paragraphs remain as historical planning context, not the current policy. Keep Property Peace identity, collection-application, admin-review and compliance backend available as **optional** controls, disabled by default. Neither Property Peace ID/selfie verification nor Property Peace application approval is a prerequisite for starting Stripe Connect onboarding by default. A landlord must set up **their own Stripe connected account**; Stripe-hosted KYC and required account capabilities/restrictions must be satisfied before collecting money. Do not confuse Stripe verification with an optional Property Peace approval, or treat an existing account ID as sufficient payout/collection readiness. Property Peace can opt into its additional review/identity gates by deliberate configuration and policy review.

Checked-in API defaults: `ShortStayCollection:RequireIdentityBeforeConnect=false`, `ShortStayCollection:RequireApplicationApproval=false`, `ShortStayCollection:RequireIdentityForApplicationApproval=false`, `Stripe:IdentityEnabled=false`, `ShortStayBooking:Enabled=false`. Keep `Stripe:RentPaymentsEnabled=false` and `Stripe:TransfersEnabled=false`. Missing optional booleans also bind as false; runtime overrides must be reviewed separately. These defaults do **not** switch on Stripe payment intake, transfers, guest booking or charging.

Direct Property Peace booking and payment remain a future **paired activation** after the booking/checkout/payment lifecycle is built and verified (availability/hold concurrency, quotes, payment, webhook reconciliation, confirmation, failures/refunds and appropriate payee readiness). Owner listing/calendar setup and imported channel blocks are not direct bookings. **Current code is incomplete: there is no completed direct-booking/payment lifecycle and no short-stay guest charges are enabled by this decision.** Do not publish a Book/Pay action or infer a production capability from optional verification flags; revalidate server-side readiness and operational/compliance approval before any activation.
